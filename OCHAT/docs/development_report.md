# OCHAT 在线互动聊天系统实践报告整理稿

这份文档是项目报告的整理稿，内容按需求分析、系统设计、编码实现、测试和总结来写。相比最终提交到 Word 的版本，这里更偏向项目说明，方便后续继续补代码截图或调整格式。

## 1. 需求分析

### 1.1 项目背景

OCHAT 是《信息系统设计与开发实践》课程中的聊天系统项目。选择聊天系统作为题目，是因为它虽然看起来常见，但实际做起来会涉及账号管理、网络通信、数据库保存、多人在线、文件传输和权限控制等内容，比较适合用来练习完整的软件开发流程。

本项目希望实现一个可以真实运行的在线聊天系统，而不是只停留在界面展示。用户应当可以注册账号、登录系统、添加好友、进行私聊和群聊、发送图片或文件，并能在重新登录后查看历史消息。

### 1.2 用户和使用场景

系统主要面向普通聊天用户和课程演示人员。普通用户只需要完成注册、登录、添加好友、发送消息、发送文件等操作；演示人员还需要能够启动服务端、切换数据库模式，并验证测试用例是否通过。

为了降低使用难度，系统提供了桌面客户端和 Web 客户端。桌面端适合直接演示 Python 图形界面，Web 端适合在浏览器中展示聊天效果。

### 1.3 功能需求

项目实现的主要功能包括：

- 用户注册、登录、退出和会话恢复。
- 个人资料修改，包括头像、昵称、签名、联系方式等。
- 好友搜索、好友申请、申请处理、备注、分组和删除好友。
- 好友在线状态和未读消息提醒。
- 一对一私聊和多人群聊。
- 群聊创建、邀请、成员查看、角色管理、群备注、退群和解散群聊。
- 文本消息、图片消息和文件消息。
- 历史消息加载、消息搜索和消息撤回。
- 文件上传、文件下载和头像文件显示。
- 服务端权限校验、输入校验和数据库持久化。

### 1.4 性能和运行要求

在课程演示场景下，系统主要运行在本机或局域网环境中。服务端使用多线程处理客户端连接，能够支持多个用户同时在线。普通文本消息应能及时送达，历史消息和搜索功能在演示数据量下应保持流畅。

系统默认支持 SQLite，便于快速演示；也可以切换到 MySQL，用于更接近正式运行的持久化环境。

## 2. 系统设计

### 2.1 整体结构

OCHAT 采用客户端、服务端、数据库分离的结构。

客户端负责界面显示和用户操作。桌面端使用 Tkinter 实现，Web 端使用 HTML、CSS 和 JavaScript 实现。两种客户端最终都通过同一套通信能力访问服务端。

服务端负责业务处理，包括用户认证、好友关系、群聊权限、消息保存、文件处理和实时推送。客户端不能直接访问数据库，也不能自己决定是否有权限读取消息或下载文件。

数据库负责保存用户、好友、申请、群聊、群成员、消息、已读状态和文件元数据。文件内容本身保存在上传目录中。

### 2.2 主要模块

用户模块处理注册、登录、退出和个人资料修改。注册时检查用户名和密码格式，登录时验证密码哈希，登录成功后返回用户资料和会话数据。

好友模块处理好友申请、同意或拒绝申请、好友列表、备注分组和删除好友。好友关系按用户视角保存，所以双方可以给同一个好友设置不同备注。

消息模块处理私聊、群聊、历史消息、消息搜索、未读数量和撤回。私聊发送前检查双方是否为好友，群聊发送前检查用户是否在群内。

群聊模块处理创建群聊、邀请成员、查看成员、修改群名、修改群备注、设置群内昵称、调整角色、移除成员、退群和解散群。

文件模块处理文件上传、图片预览、文件下载和头像文件读取。服务端限制文件后缀、大小和保存路径，下载时还会检查访问权限。

Web 模块提供浏览器访问入口。它本身不重写聊天业务，而是通过本地 HTTP 桥接服务调用原有 TCP 客户端封装。

### 2.3 数据库设计

数据库主要表包括：

- `users`：保存用户账号、密码哈希和个人资料。
- `friendships`：保存好友关系、备注和分组。
- `friend_requests`：保存好友申请。
- `chat_groups`：保存群聊基本信息。
- `group_members`：保存群成员、角色、群昵称和个人群备注。
- `group_invitations`：保存群聊邀请。
- `messages`：保存私聊和群聊消息。
- `message_reads`：保存每个用户的消息已读状态。
- `files`：保存文件元数据。

消息表通过 `conversation_type` 区分私聊和群聊。私聊时 `target_id` 表示接收用户，群聊时 `target_id` 表示群聊编号。文件内容不直接存入数据库，而是保存到 `database/uploads/`，消息通过 `file_id` 关联文件记录。

## 3. 系统编码与实现

### 3.1 注册与登录

注册和登录是系统入口。客户端把用户名、密码和昵称发送给服务端，服务端先进行格式校验，再调用数据库访问层完成用户创建或身份认证。

注册时，用户名必须是 3 到 20 位字母、数字或下划线，密码长度为 6 到 64 位。服务端保存密码前会生成随机盐，并使用 PBKDF2-SHA256 计算密码摘要。

登录成功后，服务端登记当前连接，生成 token，并返回用户资料、好友列表、群聊列表、会话列表和申请信息。客户端拿到这些数据后进入主界面。

### 3.2 好友管理

好友添加采用申请流程，而不是直接添加。用户搜索到目标账号后发送好友申请，对方同意后服务端才创建双向好友关系。

好友关系写入时使用事务处理，避免只给其中一方写入成功。修改备注和分组时，只修改当前用户自己的好友记录。删除好友时，服务端会清理双方的好友关系，并通知在线客户端刷新列表。

### 3.3 私聊消息

私聊消息发送时，客户端提交接收方编号和消息内容。服务端先检查用户是否登录，再检查消息内容是否为空，最后确认发送者和接收者是否已经是好友。

校验通过后，服务端把消息写入 `messages` 表，并推送给发送者和接收者。发送者自己的消息会自动标记为已读，接收方如果没有打开会话，会在列表中看到未读数量。

### 3.4 群聊功能

创建群聊时，服务端会先写入群聊记录，再把创建者写入群成员表，并设置为群主。群成员可以设置群内昵称，用户也可以为某个群设置只对自己显示的群备注。

群聊发送消息前，服务端会检查发送者是否属于该群。邀请成员、移除成员、修改角色、解散群聊等操作还会检查群角色，防止普通成员执行管理操作。

### 3.5 文件和图片

文件发送分成两步：先上传文件，再发送文件消息。上传时，客户端把文件内容编码后发送给服务端；服务端检查文件名、文件大小和后缀，通过后保存到上传目录，并写入文件表。

图片消息在客户端显示时会尝试生成预览，普通文件则显示文件名、大小和下载按钮。用户下载文件时，服务端会再次检查该用户是否有权访问对应文件。

### 3.6 Web 版本

Web 端由 `web_client/server.py` 提供本地 HTTP 服务，静态页面放在 `web_client/static/`。浏览器不能直接连接原 TCP 服务端，所以 Web 端通过桥接服务转发请求。

这种设计保留了原来的服务端业务逻辑。登录、注册、好友、群聊、消息、文件等功能仍然走原来的接口，Web 端主要负责界面展示和交互体验。

## 4. 测试与修复

项目使用 pytest 编写测试，重点覆盖协议、数据库、服务端接口和安全校验。除了自动化测试，也对 Web 页面中的常见操作进行了人工检查。

### 4.1 功能测试

图片消息显示测试：

用户 A 向用户 B 发送图片消息。最初 Web 端只能显示文件信息，不能直接预览图片。修复后，前端会根据文件编号读取图片数据，并转换为浏览器可显示的地址，同时保留下载功能。

聊天区域滚动测试：

连续发送多条消息，使聊天内容超过屏幕高度。测试时发现消息区域一度不能正常上下滑动，进入会话后也不一定停留在最新消息。修复时调整了消息区高度和滚动容器，并在消息渲染完成后滚动到底部。

消息搜索测试：

发送多条不同内容的消息后，分别搜索正文关键词和时间相关关键词。测试中发现搜索逻辑把发送时间也算进了搜索范围，导致结果不准确。修复后搜索范围只保留消息正文和有效文件信息，不再用发送时间参与匹配。

### 4.2 安全性测试

未登录访问测试：

在未登录状态下请求好友列表、群聊列表和消息历史。服务端会拒绝这些请求，避免用户绕过登录流程直接读取数据。

非好友私聊测试：

两个用户没有建立好友关系时，尝试直接发送私聊消息。服务端会检查好友关系，非好友不能发送私聊消息，建立好友关系后才能正常通信。

消息内容安全测试：

在聊天框输入 HTML 标签或脚本内容，检查 Web 页面是否会执行脚本。前端显示消息时使用安全的文本处理方式，不把用户输入当作页面脚本执行。

### 4.3 测试覆盖

自动化测试覆盖了这些内容：

- 协议发送、接收和异常 JSON 处理。
- 用户注册、登录和重复用户名处理。
- 好友申请、好友关系和删除好友。
- 私聊消息、群聊消息、历史记录和搜索。
- 群邀请、成员角色、群备注、退群和解散群。
- 文件上传、下载和访问权限。
- 未读消息统计和已读状态更新。
- 用户名、密码、消息内容、搜索关键词和文件大小校验。

## 5. 运行说明

安装依赖：

```powershell
python -m pip install -r requirements.txt
```

启动服务端：

```powershell
python start_server.py
```

启动桌面客户端：

```powershell
python start_client.py
```

启动 Web 客户端：

```powershell
python start_web_client.py
```

浏览器访问：

```text
http://127.0.0.1:8080
```

运行测试：

```powershell
python -m pytest -q
```

## 6. 实践总结

通过这个项目，我对聊天系统的完整流程有了更清楚的认识。注册登录只是入口，真正容易出问题的是后面的状态同步、权限判断、消息保存和文件访问。比如未读数量需要考虑发送者和接收者的不同状态，群聊消息需要判断成员身份，文件下载也不能只看文件编号。

项目从桌面端扩展到 Web 端后，我也认识到迁移界面不能只做页面。前端形式可以变，但原来的业务功能不能丢，登录、好友、群聊、历史、文件和安全校验都要继续保持一致。

本项目在需求整理、界面优化、测试用例归纳和文档表达上使用了大模型辅助。使用过程中，我主要把它作为整理思路和检查遗漏的工具，最终功能是否正确仍然需要通过代码运行和测试结果来判断。
